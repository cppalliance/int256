[#saturating]
= `<numeric>` Support
:idprefix: saturating_

[#sat_arith]
== Saturating Arithmetic

Saturating arithmetic avoids the possibility of overflow or underflow by clamping the value to a defined range should either of these situations occur.
This means that on overflow the function returns `std::numeric_limits<uint256>::max()`, and on underflow it returns `0`.
The following functions are provided for saturating arithmetic, and they *do not* require pass:[C++26].

[source, c++]
----
#include <boost/int256/numeric.hpp>

namespace boost {
namespace int256 {

BOOST_INT256_HOST_DEVICE constexpr uint256 saturating_add(const uint256& x, const uint256& y) noexcept;

BOOST_INT256_HOST_DEVICE constexpr uint256 saturating_sub(const uint256& x, const uint256& y) noexcept;

BOOST_INT256_HOST_DEVICE constexpr uint256 saturating_mul(const uint256& x, const uint256& y) noexcept;

BOOST_INT256_HOST_DEVICE constexpr uint256 saturating_div(const uint256& x, const uint256& y) noexcept;

} // namespace int256
} // namespace boost
----

Multiplication is where a 256-bit type overflows most easily: the product of any two values at or above 2^128^ does not fit, and `saturating_mul` returns the maximum for those instead of the wrapped value.

An unsigned quotient is never larger than the dividend, so `saturating_div` cannot overflow and returns the same result as the plain `operator/`.
It exists for interface parity, and for the planned signed type where `min / -1` does overflow.
Division by zero is a precondition violation and therefore undefined behavior (the divisor must be non-zero), exactly as for the plain division operator; `saturating_div` adds no zero-divisor check.

[#saturating_cast]
== Saturating Cast

This function converts a `uint256` to a `TargetType`, saturating rather than wrapping when the value is out of the target's range.
`TargetType` is constrained (via SFINAE) to the library's set of reduced integer types: the standard signed and unsigned integer types (excluding `bool` and plain `char`), `uint256` itself, and the compiler's native 128-bit integer types where available.
Should the `TargetType` not be able to represent the value it is set to `std::numeric_limits<TargetType>::max()`.

[source, c++]
----
#include <boost/int256/numeric.hpp>

namespace boost {
namespace int256 {

template <typename TargetType>
BOOST_INT256_HOST_DEVICE constexpr TargetType saturating_cast(const uint256& value) noexcept;

} // namespace int256
} // namespace boost
----

This is the safe counterpart of the implicit conversion operators, which keep the low bits instead. See also xref:utilities.adoc#in_range[`in_range`], which reports whether the value would fit without converting it.

[#gcd]
== Greatest Common Divisor (GCD)

Computes the greatest common divisor of `a` and `b`.

[source, c++]
----
#include <boost/int256/numeric.hpp>

namespace boost {
namespace int256 {

BOOST_INT256_HOST_DEVICE constexpr uint256 gcd(uint256 a, uint256 b) noexcept;

} // namespace int256
} // namespace boost
----

Returns `0` when both `a` and `b` are `0`; otherwise returns the greatest common divisor.
In particular, `gcd(a, 0)` returns `a` and `gcd(0, b)` returns `b`.
This matches the results of https://eel.is/c++draft/numeric.ops#gcd[`std::gcd`] for every operand representable in the type.
The function is `noexcept` and usable in a constant expression.

[#lcm]
== Least Common Multiple (LCM)

Computes the least common multiple of `a` and `b`.

[source, c++]
----
#include <boost/int256/numeric.hpp>

namespace boost {
namespace int256 {

BOOST_INT256_HOST_DEVICE constexpr uint256 lcm(const uint256& a, const uint256& b) noexcept;

} // namespace int256
} // namespace boost
----

Returns `0` when either `a` or `b` is `0`; otherwise returns the least common multiple.
This matches the results of https://eel.is/c++draft/numeric.ops#lcm[`std::lcm`] for every operand whose least common multiple is representable in the type.

NOTE: `std::lcm` leaves the behavior undefined when the least common multiple itself is not representable; this library defines that case instead of trapping or throwing. The result is the true least common multiple reduced modulo 2^256^, consistent with the wrap-around of the xref:uint256.adoc#u256_math_operators[arithmetic operators].

[#midpoint]
== Midpoint

Computes the midpoint of `a` and `b`, rounding towards `a`.

[source, c++]
----
#include <boost/int256/numeric.hpp>

namespace boost {
namespace int256 {

BOOST_INT256_HOST_DEVICE constexpr uint256 midpoint(const uint256& a, const uint256& b) noexcept;

} // namespace int256
} // namespace boost
----

The sum is never formed, so `midpoint` cannot overflow: `midpoint(max, max - 10)` is correct, while `(a + b) / 2` at that magnitude is not.
That is what makes it usable as the step of a binary search over the whole range of the type; see the xref:examples.adoc#examples_numeric_algorithms[numeric algorithms example].

[#int_div]
== Integer Division

`operator/` only ever rounds towards zero.
These functions divide with each of the other rounding modes, and are the 256-bit counterparts of the `std::div_*` family proposed for the standard library by wg21.link/p3724[P3724 (Integer division)].
They *do not* require pass:[C++26], and every one of them is `constexpr` and available on device.

[#div_result]
=== `div_result`

Both halves of a division, mirroring `std::div_result<T>` from the paper.
It is an aggregate, so `div_result<uint256>{q, r}` and structured bindings both work.
Equality is always available; the ordering operators are available whenever the compiler supports `operator<=>`, and compare the quotient before the remainder.

[source, c++]
----
#include <boost/int256/numeric.hpp>

namespace boost {
namespace int256 {

template <typename T>
struct div_result
{
    T quotient;
    T remainder;
};

template <typename T>
BOOST_INT256_HOST_DEVICE constexpr bool operator==(const div_result<T>& lhs, const div_result<T>& rhs) noexcept;

template <typename T>
BOOST_INT256_HOST_DEVICE constexpr bool operator!=(const div_result<T>& lhs, const div_result<T>& rhs) noexcept;

// Only when BOOST_INT256_HAS_SPACESHIP_OPERATOR is defined
template <typename T>
BOOST_INT256_HOST_DEVICE constexpr std::strong_ordering operator<=>(const div_result<T>& lhs, const div_result<T>& rhs) noexcept;

} // namespace int256
} // namespace boost
----

[#div_rounding_modes]
=== Rounding Modes

Each mode comes in two forms: `div_<mode>` returns the quotient and `div_rem_<mode>` returns the quotient and the matching remainder. For Euclidean division `rem_euclid` returns the remainder alone.

[source, c++]
----
#include <boost/int256/numeric.hpp>

namespace boost {
namespace int256 {

BOOST_INT256_HOST_DEVICE constexpr uint256 div_<mode>(const uint256& x, const uint256& y) noexcept;

BOOST_INT256_HOST_DEVICE constexpr div_result<uint256> div_rem_<mode>(const uint256& x, const uint256& y) noexcept;

BOOST_INT256_HOST_DEVICE constexpr uint256 rem_euclid(const uint256& x, const uint256& y) noexcept;

} // namespace int256
} // namespace boost
----

`<mode>` is one of the eleven names below.
The last two columns give the quotient for a dividend that does not divide evenly, and for one that lands exactly halfway between two integers.

[cols="1,2,1,1", options="header"]
|===
| `<mode>` | Rounds | `12 / 5` (exactly `2.4`) | `7 / 2` (exactly `3.5`)

| `to_zero`
| Towards zero, which is what `operator/` does
| `2`
| `3`

| `away_zero`
| Away from zero
| `3`
| `4`

| `to_pos_inf`
| Towards positive infinity (ceiling)
| `3`
| `4`

| `to_neg_inf`
| Towards negative infinity (floor)
| `2`
| `3`

| `euclid`
| So that the remainder is non-negative
| `2`
| `3`

| `ties_to_zero`
| To nearest, an exact tie towards zero
| `2`
| `3`

| `ties_away_zero`
| To nearest, an exact tie away from zero
| `2`
| `4`

| `ties_to_pos_inf`
| To nearest, an exact tie towards positive infinity
| `2`
| `4`

| `ties_to_neg_inf`
| To nearest, an exact tie towards negative infinity
| `2`
| `3`

| `ties_to_odd`
| To nearest, an exact tie to the odd quotient
| `2`
| `3`

| `ties_to_even`
| To nearest, an exact tie to the even quotient
| `2`
| `4`
|===

An exact tie is only possible when the divisor is even, so the six `ties_` modes differ from each other only there; everywhere else they all return the nearest integer.

[#div_semantics]
=== Semantics

The remainder returned by `div_rem_<mode>` is the one that matches the quotient, so `x == quotient * y + remainder` holds modulo 2^256^.
A quotient rounded up leaves a negative remainder, which has to wrap: `pass:[div_rem_to_pos_inf(uint256{12}, uint256{5})]` therefore returns a quotient of `3` and a remainder of `2^256^ - 3`, since `12 - 3 * 5` is `-3`.
The quotient itself never overflows: rounding only moves the quotient when the division is inexact, and an inexact division has a divisor of at least two.

Because a `uint256` quotient is never negative, several of the modes collapse together.
`div_to_zero`, `div_to_neg_inf`, and `div_euclid` are all plain truncation, `div_away_zero` and `div_to_pos_inf` are the same rounding up, `div_ties_to_neg_inf` matches `div_ties_to_zero`, and `div_ties_to_pos_inf` matches `div_ties_away_zero`.
The full set is still provided so that generic code can name a rounding mode without also having to know the signedness of the operands, and so that the names keep their meaning when the signed `int256` arrives.

`rem_euclid` returns a value in `[0, y)`, which for an unsigned dividend is exactly what `operator%` returns.
It is provided for the same reason: so that code written against the P3724 interface compiles for either signedness.

Each `div_rem_<mode>` performs exactly one division, so it is the cheaper way to obtain both halves; computing `x / y` and `x % y` separately costs two divisions, since neither the compiler nor the library can share the work across the two operators.
xref:cstdlib.adoc[`div`] is the same idea for the truncating mode.

A zero divisor is a precondition violation and therefore undefined behavior, exactly as for `operator/` and xref:numeric.adoc#sat_arith[`saturating_div`]; no zero-divisor check is performed.

NOTE: The paper leaves these functions non-`noexcept` because a precondition violation is undefined behavior.
This library marks them `noexcept` for consistency with the rest of its interface, which does the same.

See the xref:examples.adoc#examples_integer_division[integer division example] for a program that prints every mode.
